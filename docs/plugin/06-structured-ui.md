# 插件系统计划：通用结构化 UI 与 DIY 演进

状态：讨论稿。用户已确认本文件第 1 节的目标；具体 schema、组件名称和实现步骤是待细化的设计建议，尚未实现。

## 1. 已确认的方向

1. 增强现有 DIY 的解析与呈现能力，并应用到其他位置，不只服务于供应商面板。
2. 支持更自由的布局、外观与动效、状态与动态内容、表单和操作反馈。
3. 采用“结构化声明 + 状态绑定”：插件声明布局和交互入口，业务代码处理事件、更新状态，AiCode 负责绘制。
4. 构建插件页面和插件配置页使用这套结构化能力，右抽屉提供插件列表入口。
5. 构建、下载依赖等具体业务由插件实现；App 提供通用 UI 与能力接口，不按构建框架硬编码业务。

这里的自由度不是放弃结构化校验或把任意 Android UI 对象交给插件，也不是已经决定引入 HTML/CSS/WebView。建议继续以原生 Compose 渲染为主，视觉默认跟随项目现有主题和组件体系；本轮不另外设计配色或品牌风格。

## 2. 现有能力与实际限制

不能把当前 DIY 描述成“只有固定几张卡片”。现有实现已经具备一定的排版与样式能力，主要限制是共同属性不统一、根布局/呈现场景固定，以及缺少通用状态和业务事件机制。

| 方面 | 已核实的现状 | 需要演进的方向 |
| --- | --- | --- |
| 基本排版 | 有 ColumnSet、Column、Container、Row、FlowRow、ScrollRow、TabSet；部分支持权重、尺寸约束和边距 | 统一每种节点的尺寸/对齐语义，再扩展网格、叠放与响应式能力 |
| 根布局 | 展开态固定按 Column 绘制；无 compact 时取 body 前三项平均分配 | 根节点与宿主呈现方式分离，不把面板摘要规则应用到完整页面 |
| 外观 | 已有语义色、自定义颜色、字号、行高、部分圆角及进度条动画 | 建立统一样式和状态样式，而不是继续给个别组件零散加字段 |
| 显隐 | `visible` 在解析时按布尔值过滤节点 | 增加绑定驱动的条件显示，明确隐藏与移除的状态保留语义 |
| 表单 | 当前节点模型与渲染分派没有输入框、选择项、开关等表单组件 | 增加统一字段绑定、校验、提交与错误呈现 |
| 动作 | 按钮围绕打开链接、复制和刷新，刷新通过单独回调处理 | 统一事件描述与插件 handler，不在渲染器里内置构建动作 |
| 业务执行 | 解析方法与供应商脚本运行在同一个 Runner 中 | 抽出纯 UI 解析/校验；脚本运行、供应商上下文和插件运行时分别适配 |

## 3. 建议的通用渲染管线

```text
声明文档 + 初始状态 + 宿主呈现场景
  → 版本识别、解析和诊断
  → 类型化节点树、绑定/事件校验
  → 宿主约束下的原生渲染
  → 用户事件 → 插件 handler → 状态更新 → 受影响节点刷新
```

### 三个职责分开

- **通用 UI 引擎**：节点、布局、样式、绑定、表单和事件分发，不知道构建命令或供应商业务。
- **呈现容器**：面板、插件页面、配置页各自提供可用尺寸、导航、滚动和生命周期，不更改节点协议的基本含义。
- **业务适配器**：旧 DIY 脚本结果、插件状态与业务事件分别接入，不把运行脚本或读取 API Key 的逻辑放进渲染器。

现有供应商 Runner 会注入供应商上下文，见 [ProviderDashboardRunner.kt:709](../../app/src/main/java/com/aicode/feature/settings/domain/service/ProviderDashboardRunner.kt:709)。提取 UI 能力不等于让插件继承这些环境变量或供应商凭据。

建议共享代码放在跨 feature 的 UI 基础设施中，供应商和插件各自持有业务适配；具体目录与模块拆分待接口边界确定后决定，避免 `core` 反向依赖 settings/agent 业务。

## 4. 布局：统一规则优先于继续堆组件

### 4.1 所有适用节点共享的布局语义（建议）

- 节点稳定 ID，供列表、表单焦点、动画和状态保留使用。
- 宽高采用明确的包裹、填充、固定值、比例/权重和最小/最大约束；哪些组合可用由父布局定义。
- 区分内边距、外边距、子项间隔、主轴/交叉轴对齐、内容对齐。
- 明确溢出、裁剪、换行、滚动和尺寸约束，不让每种节点自行决定 `fillMaxWidth`。
- 大小和布局状态可绑定允许的数据，但所有运行时值仍需校验，不允许无穷值、非法权重或无界递归测量。

这些是语义需求，不是本轮定稿的字段名或 CSS 子集。

### 4.2 布局能力候选

| 能力 | 目的 | 需要定义的约束 |
| --- | --- | --- |
| 行、列、自动换行 | 覆盖自由组合、均分、权重和内容优先 | 同一轴上的权重、填充与滚动如何组合 |
| 网格 | 多列工具区、表单排版、动态列表 | 列数/最小项宽、跨度、间隔、窄宽度降列 |
| 叠放 | 图标角标、进度覆盖层等 | 层级、锚点、裁剪、点击命中和可访问性 |
| 响应式规则 | 手机、平板、分屏与抽屉/页面不同宽度 | 按实际容器宽度匹配，不只识别设备型号 |
| 有界滚动和惰性列表 | 长日志、依赖列表等动态内容 | 滚动方向、稳定 item ID、保留位置与嵌套限制 |

不预设必须实现完整绝对定位或完整 CSS；自由度应通过这些可组合、可校验的原生布局表达，具体覆盖范围继续细化。

## 5. 外观与动效（已确认需要，接口建议）

- 背景、边框、圆角、字体、间距、图标、透明度及渐变建立统一样式语义。
- 默认使用 App 的语义色、Spacing、Radius 等主题资源；自定义样式也需具备明暗模式和文本对比度规则。
- 支持必要的状态样式，如禁用、加载、错误、选中；状态来自绑定，不靠业务代码操作 Compose 对象。
- 动效用有界声明表达显隐、布局/数值变化和进度；持续动画数量、频率和减少动态效果的行为需受宿主约束。
- 宿主保留身份、权限提示、导航和停止操作等可信区域，插件样式不能覆盖这些区域或伪装授权界面。

原生渲染仍优先复用项目的 `AppTextField`、`AppSwitch`、`AdaptiveModalBottomSheet` 和设置分组组件，不因插件 UI 再创建一套互不一致的基础控件。

## 6. 状态绑定与动态内容

**已确认使用声明 + 状态绑定，不把插件任意返回完整 UI 树作为首要契约。** 建议采用如下分工：

- 声明定义节点、绑定位置、条件、列表项模板与事件入口。
- 插件业务逻辑持有业务状态，宿主保存该页面/实例的状态快照并应用更新。
- 表单输入作为字段状态更新；业务 handler 在校验和动作时读取一致的状态版本。
- 复杂计算在插件逻辑中完成；绑定使用受限的数据引用和明确表达式能力，不通过 `eval` 执行任意脚本。
- 列表数据、条件显隐、按钮可用性、进度和错误文本随状态变化更新，不要求重新运行面板脚本或重建整页。

建议区分页面临时状态、插件配置、任务状态三类数据。页面销毁时任务继续还是终止仍待确认，不默认绑定二者的生命周期；配置保存也不应把所有临时日志一起写入持久化存储。

### 更新与一致性要求

- 状态更新携带页面/插件版本和宿主关联身份；过期实例不能覆盖新页面。
- 支持原子应用一组状态变化，防止“按钮已启用但参数还是旧值”。完整快照还是局部更新协议待定。
- 稳定节点 ID 保留输入焦点、选中项和列表位置；重组、屏幕旋转不能重复执行事件。
- 不在布局测量、Compose 重组、绑定求值或普通状态刷新时执行命令、网络、授权或配置写入等业务副作用。
- 表单交互延迟、事件去重和高频进度/日志的合并规则需要性能验证，不先写无依据的刷新频率。

## 7. 表单与插件配置页

已确认需要输入框、选择项、开关、校验及操作反馈，具体组件清单待接口定稿。

建议至少定义：字段类型、默认值、值绑定、可见/只读/禁用、校验错误、提交事件和异步保存状态。表单字段类型和校验结果由协议表达，复杂业务校验由插件逻辑负责；宿主在能力调用入口仍独立校验，不能只相信 UI 表单已校验。

**已确认的入口为“设置 → 插件 → 插件列表 → 插件配置”。** 配置内容复用同一引擎、同一套状态/事件机制，而不是只支持一个固定的 Key-Value 编辑器；插件权限、安装确认和管理按钮则由宿主可信界面提供，见 [08-plugin-management.md](08-plugin-management.md)。配置是自动保存还是显式保存、哪些值属于项目/全局、敏感字段如何保存，仍待确认。

UI 中的“启用”“已授权”等文字或开关只是插件内容，不能直接改变宿主管理的插件启停和能力授权。真实权限管理由宿主可信界面完成。

## 8. 事件与业务逻辑

```text
点击按钮 / 输入改变 / 选择项改变
  → 宿主校验页面、节点和已声明事件
  → 发送类型化事件及必要状态到插件逻辑
  → 插件计算、校验或申请宿主能力
  → 宿主检查授权后执行
  → 结果 / 进度 / 失败回到插件
  → 插件更新状态，UI 根据声明刷新
```

“构建”“下载依赖”是插件声明的标签和 handler，不是渲染器内置的动作类型。UI 只引用已声明事件标识，业务逻辑通过受控能力调用 Bash/terminal；详见 [07-build-plugins.md](07-build-plugins.md)。

打开链接、复制、选择文件等通用动作如要开放，也应经过宿主的受控事件接口。不能把现有面板直接发 Intent 或读取供应商上下文的方式原样开放给不可信插件。

## 9. 校验、资源与诊断（建议）

- 协议版本、节点类型、属性类型、绑定路径、事件引用、重复 ID 都要有明确错误，诊断应定位到声明文件/节点/属性。
- 新协议不把未知节点悄悄变成普通文本；未知可选视觉属性如何降级与未知事件如何拒绝要分开定义。
- 声明和运行时数据均限制大小、深度、节点数、列表长度、图片资源和动画开销，防止结构化数据拖死主线程。
- 本地资源只访问插件授权的资源根；外部图片等加载如需网络/文件能力，不能因为写在 UI 声明里就绕过授权。
- 声明内容和进程输出都不是宿主指令。插件不能通过日志文本、样式或事件名修改权限、伪造用户输入或访问其他插件对象。
- 必须测试字体放大、明暗主题、键盘遮挡、横竖屏、屏幕阅读器和触摸目标；右抽屉列表与完整页面分别验证。

## 10. 现有 DIY 的迁移方式（建议）

1. 先记录现有协议实际行为和样例，以模型、解析、渲染三方一致为准，不只看文档字段。
2. 提取纯解析/校验与通用渲染边界，不直接将供应商 Runner 更名为插件引擎。
3. 选择明确的协议演进方式：旧输入转换到新模型，或保留版本化解析入口；这是长期协议支持决策，不做无期限临时双写。
4. 新增布局、绑定、表单和事件后，既有 DIY 面板使用同一引擎的面板呈现场景，不强行变成完整页面。
5. 面板的 compact/expanded、刷新和高度约束应由面板宿主管理，不成为通用根节点默认值；迁移时建议以现有行为为对照，具体保留或调整哪些容器规则需用户确认，不在本轮冻结。
6. 迁移完成后，不保留多份随意分叉的解析器和组件实现；用户文档、协议说明、样例与测试同步更新。

现有字段是否保留、具体版本号、哪些错误兼容旧输入仍需先对账，不能在本轮猜测成最终 schema。

## 11. 建议验收场景

- 同一结构化基础能承载现有 DIY、右抽屉打开的插件页面和插件配置页，且没有三套业务专用渲染器。
- 同一声明在手机窄屏、平板分栏和键盘弹出时排版可用；不能只做固定宽度截图验证。
- 改表单字段和条件项不会丢失焦点或其他输入；动态列表顺序变化仍能保持节点身份。
- 重组或重复打开页面不会重复构建/安装；异步事件回包不写入过期页面。
- 长日志、快速进度、多层布局、错误声明和非法状态更新有界处理，宿主保持可操作。
- 插件自定义业务没有出现在 App 的固定动作枚举、构建命令表或依赖下载逻辑中。
