# 插件系统计划：权限、代审核与双向交互

状态：讨论稿。代审核、显式插件权限、提供商注册、结构化页面/配置、tips、通知、Shizuku 和 Bash/terminal 能力是已确认需求；命令在已授权范围内直接执行，权限粒度与异常策略等建议仍可修改。

## 1. 三类授权必须分开

| 层次 | 解决的问题 | 例子 |
| --- | --- | --- |
| 插件能力授权 | 某插件是否可以调用一项宿主能力 | 发送通知、执行 Shizuku、读取请求内容、代审核 |
| AI 工具审批 | 某一次 AI 工具调用是否执行 | 允许这次 Bash、拒绝这次 MCP 工具调用 |
| 系统/外部授权 | App 是否已获得系统或服务所需权限 | Android 通知可用、Shizuku 已运行且授予 App 权限 |

插件清单声明只是申请，不是授权。App 已有系统权限不代表所有插件自动可用；AI 工具进入 AUTO 也不应自动授予插件能力。

建议实际可执行能力取“插件已声明 ∩ 使用者已授权 ∩ 当前作用域允许 ∩ 宿主限制 ∩ 系统/外部能力可用”的交集。每次宿主调用重新检查，不能仅在激活时缓存一个永久有效的布尔值。

## 2. 权限分类候选

以下名称只用于讨论，不是确定的 manifest 字段或 SDK 标识。

| 能力 | 需要说明的范围 | 备注 |
| --- | --- | --- |
| 注册工具 / MCP / Skill / 子代理 / 提供商 | 新增内容、可见范围、能否动态变更 | 注册与执行分开；提供商上游适配由插件负责 |
| 提供商请求与凭据使用 | 该插件可处理的模型请求、实例配置与凭据，以及兼容服务入口 | 不因注册提供商就获得其他渠道凭据，调用的上游与数据范围需明确 |
| 监听生命周期 | 事件类型、主/子会话、项目、可读字段 | 监听请求正文是内容访问，不只是“收一个事件” |
| 修改生命周期数据 | 可变事件和字段白名单 | 不继承所有监听与修改权限 |
| 代审核 | 可处理的工具、项目、特殊高危操作 | 高风险管理权限，需要清楚展示影响 |
| 提供结构化页面 / 配置 | 页面入口、表单状态、配置读写范围与事件 | 已确认声明 + 状态绑定，不能通过页面内容改变宿主授权 |
| Bash / terminal | 执行环境、工作区、命令/终端归属和持续访问 | 已确认获授权范围内直接执行，不逐命令确认 |
| 服务依赖准备 | 目标环境 ID、依赖输入/锁文件、实际执行目标 | 单独申请 environment.prepare，用户手动触发，不自动安装系统工具 |
| 显示 tips | 页面/会话目标、是否含按钮 | 建议仍显式声明，限制频率和来源展示 |
| 发送系统通知 | 通知类别、目标会话和动作 | 不能取消宿主或其他插件的通知 |
| 执行 Shizuku | 允许的操作范围、是否逐次确认 | 极高权限能力，不下发 Binder |

Bash/terminal 已明确纳入通用能力。额外的工作区读写、网络、任意工具调用或模型服务接口仍需分别定义权限，不能因插件已启用或已有命令权限而直接暴露所有宿主对象。任意命令内部实际具有的文件/网络等权限，也不能靠这些 SDK 接口权限伪称已被限制。

授权状态与安装身份、可信来源/签名策略和权限声明版本关联。相同显示名称或相同文本 ID 的包不能直接继承另一个作者的授权；身份连续性规则见分发章节。

## 3. 已确认的代审核流程

```text
AI ToolCall（完整参数）
  ↓
宿主按原流程判断
  ├─ 直接放行 / 无需确认：不交代审核插件
  ├─ 策略拒绝：不交代审核插件
  └─ 确认需要使用者选择
       ↓
     筛选已声明且获用户授权、作用域匹配的代审核插件
       ↓
     按使用者顺序逐个询问
       ├─ 同意：批准当前调用，停止询问后续插件
       ├─ 拒绝：仅拒绝当前调用，停止询问后续插件
       └─ 不处理：继续下一个；全部不处理或无适用插件才进入 UI
```

这是用户明确的行为顺序。普通生命周期 hook 不能把它隐式改成“所有调用先由插件决定”，或让插件把宿主 DENY 改成 ALLOW。代审核不包含改参数；评估前通用工具变换 hook 是否开放仍待单独确认，即使未来允许，变换后的调用也必须重新经过完整宿主判断。

### 3.1 现有代码中的最小接入点

在 [StatefulAgentWorkflow.kt:1404](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:1404) 的 ASK 分支，构造审批请求后、调用 `permissionManager.awaitApproval` 前增加委托。

必须保留此前的策略拒绝、`AUTO_APPROVE` 和 ALLOW 分支；现有判断见 [StatefulAgentWorkflow.kt:1369](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:1369)。

已有 `planMode exit` 另由计划审查面板处理，不属于这里的工具审批 UI，不能因为增加代审核就自动让插件批准模式切换。

### 3.2 插件返回值的含义

- **同意**：建议只代表当前请求，不等同于 UI 的“始终允许”，不写入现有工具允许规则。
- **拒绝**：仅拒绝当前工具，其他工具继续审批和执行，AI 可以继续处理。建议保留插件身份和原因，不能在日志或 UI 中伪称“用户亲自拒绝”。
- **不处理**：继续询问下一个适用插件；全部不处理才进入原有 UI，不能理解成默认允许。
- **超时、异常、失联、返回格式错误**：建议按不处理继续代审核链，最终无人决定时回到 UI，而不是自动允许。是否异常直接强制进入 UI、超时上限与整条链的等待预算仍待确认。

现有工具审批管理器负责多会话挂起、UI 决议和取消清理，见 [ToolPermissionManager.kt:17](../../app/src/main/java/com/aicode/feature/agent/domain/tool/ToolPermissionManager.kt:17)。建议最终人工兜底继续使用它，而非另建一个平行审批队列。

### 3.3 已确认的多插件顺序

1. 按使用者设置的顺序逐个询问，不并行竞争结果。
2. 返回不处理则继续下一个。
3. 首个同意或拒绝立即生效，后续插件不再参与该次审核。
4. 全部不处理，或没有适用插件时，进入现有 UI。

因此靠前插件同意后，靠后插件不会再有否决机会，排序需要在管理界面中清楚展示。尚未手动排序时的默认顺序待定，不能由插件自行声明最高优先级。

### 3.4 批次拒绝和特殊请求

**已确认：插件仅拒绝对应工具，不取消其他工具，不因此结束本轮。** 其余调用继续审批并执行，拒绝结果回给 AI 后可以继续处理。

现有 `USER_REJECTED` 会取消整批并结束本轮，而策略拒绝只拒绝对应工具，见 [StatefulAgentWorkflow.kt:410](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:410)。实施时插件拒绝应进入单调用拒绝路径，并保留独立的拒绝来源，不能直接套用 `USER_REJECTED`；用户亲自在 UI 拒绝的现有行为不随之改变。

Shizuku、`elevate` 一次性提权、修改 MCP 等配置，以及删除子代理等请求可能进入 ASK。代审核授权是否覆盖它们需要明确，不能用“不可记忆”这一标志推断“必须本人批准”或“插件都能批准”。现有 Shizuku 的特殊判断见 [ToolPermissionPolicyEngine.kt:151](../../app/src/main/java/com/aicode/feature/agent/domain/permission/ToolPermissionPolicyEngine.kt:151)。

“插件自行执行 Shizuku”与“插件代审 AI 的 Shizuku 调用”是两个不同的能力范围，不自动互相授权。

## 4. 防止代审核变成绕过授权的通道（建议）

1. 插件能力授权、安装/升级的增权确认、非官方逐次手输源码仓库确认、系统权限和外部 OAuth 授权，只能由使用者/系统完成，不进入插件可同意的队列。
2. 审核对象绑定宿主生成的请求身份、工具身份与版本、完整参数、会话/项目和授权版本。迟到、重放或其他会话的结果无效。
3. 插件拿到的是与审核范围匹配的数据快照，不是可变的待决对象，也不能调用通用 `resolve(id)` 去解决其他请求。
4. 审核前后参数、执行目标、工具版本或模式发生变化，已有同意不能继续使用；重新核验并在需要时重新审核。
5. 撤销代审核授权后，未执行的批准结果需失效；执行前再确认授权仍有效，避免审批收集期间撤权仍继续执行。
6. 插件同意后不静默写入永久工具规则；审计至少记录插件、版本、请求关联、结果来源和时间，敏感参数脱敏。
7. 避免审核回调发起相同审核、或在等待当前会话时重入它。是否允许审核期间调用其他工具，需明确受控范围，不能默认开放。
8. 是否排除插件审核自身工具、关联插件或自身产生的请求待确认。建议默认避免自批；若允许，需要向使用者明确解释授权效果。

用于参数预览的字符串可能被截断，不能作为审核执行对象的唯一依据。若完整数据含敏感字段，需要在可读权限和正确审核之间做设计；数据不足时插件应能返回不处理，而不是猜测后同意。

## 5. App 与插件的双向交互（建议）

```text
插件声明页面 / 配置，或请求显示 tips / 发通知
  → 宿主校验声明、权限、目标和资源边界
  → App 渲染或报告无法显示
  → 使用者点击操作或修改表单
  → 宿主生成带归属的回调事件
  → 插件处理并可发起下一次受控请求
```

- 插件提供展示数据和局部动作标识，宿主持有 UI、事件 ID 和 PendingIntent，不接受任意 Android Intent 或可执行回调。
- 显示插件来源，保留宿主固定的身份区域；插件文字不能伪装成系统授权、正式用户输入或可信模式通知。
- 回调绑定插件版本和原目标，更新、停用或会话删除后不唤醒过期代码。通知点击导致的持久化回调是否跨重启生效待确认。
- App 在后台或目标页面不存在时，明确返回未展示/已排队等状态；队列有界，不无限积压 tips。
- 已确认结构化页面、配置表单及状态绑定；配置从设置内的插件管理列表打开，权限与安装确认由宿主管理，见 [08-plugin-management.md](08-plugin-management.md)。交互等待不能持有 Agent 锁。插件是否可主动弹出阻塞式确认框或模态页面，仍需单独确认，不由页面能力自动推导。

已有页面使用 Toast 展示临时消息，例如 [AIChatPanel.kt:801](../../app/src/main/java/com/aicode/feature/agent/presentation/component/AIChatPanel.kt:801)。这可以作为视觉行为参考，但不把页面局部的 Toast 调用直接暴露为插件 API。

已有自定义面板采用脚本 JSON 到 Compose 的声明式呈现，可参考 [ProviderDashboardRunner.kt:81](../../app/src/main/java/com/aicode/feature/settings/domain/service/ProviderDashboardRunner.kt:81)。已确认要把它演进为供面板、页面与配置共用的通用能力，而不是直接将旧面板回调当作插件 API。具体见 [06-structured-ui.md](06-structured-ui.md)。

## 6. 通知

**已确认：发送通知需要显式声明并获授权。** 建议由宿主统一建立插件通知入口：

- 插件只管理自己的通知 ID；宿主建立映射，不能覆盖 Agent 审批、完成通知或其他插件通知。
- 区分 App 内提示和 Android 系统通知；不能假定系统总能展示通知。
- 检查系统通知开关和渠道状态，返回真实结果；不为了显示通知自动申请系统权限、跳设置或伪造成功。
- 渠道划分、锁屏可见性、响铃、频率、重复合并和敏感内容展示需要制定默认规则；不允许无限创建系统渠道。
- 点击只触发宿主批准的动作，再按插件当前授权执行；点一条通知不是任意后续操作的总授权。

现有通知渠道在 [AIEditorApp.kt:755](../../app/src/main/java/com/aicode/AIEditorApp.kt:755) 初始化，实时通知在 [AgentLiveNotificationManager.kt:83](../../app/src/main/java/com/aicode/feature/agent/presentation/notification/AgentLiveNotificationManager.kt:83) 渲染，可复用平台集成经验，不复用其固定 ID 作为插件 ID。

另外，`AgentNotificationCenter` 是向 AI 送达后台事件的队列，见 [AgentNotificationCenter.kt:46](../../app/src/main/java/com/aicode/feature/agent/domain/notification/AgentNotificationCenter.kt:46)，并不是 Android 通知中心。本轮没有确认允许插件向 AI 任意注入消息或启动新一轮推理；若需要，要单独声明能力和触发策略。

## 7. Shizuku

**已确认：插件可以申请调用 Shizuku，使用前必须获使用者授权。** 建议复用 [ShizukuManager.kt:220](../../app/src/main/java/com/aicode/feature/agent/domain/shizuku/ShizukuManager.kt:220) 的执行后端，不复制一套连接逻辑。

调用前至少确认：插件声明与授权、授权范围、Shizuku 可用状态、App 的 Shizuku 系统授权，以及此次操作是否还需人工确认。授权插件不能代替使用者启动 Shizuku 服务或批准系统授权弹窗。

- 不把 Binder、UserService 或任意系统服务对象交给插件。
- 始终作用于手机 Android 系统，SSH 模式也不变；UI 和日志必须说明目标，避免误当成远端命令。
- 任意 shell 命令属于高风险授权，不能靠粗糙的命令前缀匹配承诺细粒度隔离。是否先提供结构化操作接口、是否允许任意命令、授权一次后是否仍逐次确认，均待确认。
- 输出有界且可脱敏。取消等待不代表 shell 命令已终止，需专门验证 UserService 中的中断与清理，不能提前宣称取消成功。
- 宽泛 Shizuku 权限会显著扩大攻击面，包括间接操作其他 App 或 UI 的可能性；沙箱不能撤回已经委托出去的系统能力。

现有 AI Shizuku 工具默认逐次审核，见 [ShizukuTool.kt:47](../../app/src/main/java/com/aicode/feature/agent/domain/tool/shizuku/ShizukuTool.kt:47)。插件 SDK 调用如果直接复用后端，也必须接入新的插件授权，不能因绕过 AgentTool 而绕过检查。

## 8. 撤权与安全承诺

建议撤权立即阻止新的调用、使尚未执行的授权票据失效，并取消可取消的在途任务；停用插件同时撤销监听和注册贡献。已发生的文件修改、网络请求、系统操作不能靠撤权自动回滚。

授权存储不能由插件的普通文件/脚本接口修改。对现有 stdio 进程、任意高权限命令和提示词诱导产生的行为，应单独说明边界，而不是把它们纳入一个未经验证的“完整沙箱”承诺。

## 9. 插件 UI 命令调用的已确认规则

- 插件声明 Bash/terminal 能力，使用者明确授权后，范围内的普通命令直接执行，不逐条弹窗确认，也不进入面向 AI ToolCall 的代审核队列。
- 每次调用仍检查当前插件、授权版本、目标与范围；越权、撤权或宿主需特殊处置的请求不能通过自动提权变成范围内操作。
- AI 调用插件工具仍先走宿主 AI 权限判断与 ASK 代审核；handler 内部再检查插件能力。不能由某个 UI handler 或后台事件去掉受限 Agent 的原始上下文。
- 命令跟随当前工作区，但运行中的任务句柄绑定原目标，不能在切换服务器/容器后误操作其他环境。
- Bash/terminal 授权不自动涵盖 Shizuku。已确认插件任务可以进入用户终端页面，使用者可以管理共享标签；这不默认授予插件读取/发送其他插件或用户标签的能力。
- 设置内的“插件权限”操作进入宿主可信授权页，和插件声明的业务配置分离；非官方安装及每次更新的手输确认也不能由插件 UI 或代审核处理。

具体授权范围、如何展示宽泛命令权限和任务生命周期仍需细化，见 [07-build-plugins.md](07-build-plugins.md)。

服务依赖的手动准备仍需独立授权和实际命令能力，不因包已安装、模型请求需要服务或先前允许命令就自动执行安装。准备实例绑定原执行目标，失败/取消不标记 ready，详见 [12-service-dependencies.md](12-service-dependencies.md)。

## 10. 提供商插件的请求边界

提供商插件向 App 提供当前支持的接口，上游转换由插件实现。注册定义、启动兼容服务、处理模型请求和使用凭据是不同的能力边界，不能以一个注册动作默认授予全部。

插件可以获得使用者明确配置或授权给自身业务的上游凭据；不能取得全量渠道对象、其他提供商 Key 或任意会话历史。兼容入口或上游目的地变化需重新核对范围，停用/失联时不能无感回退到其他付费渠道。兼容 HTTP 服务为接入建议，服务托管和认证细节仍待明确，见 [09-provider-plugins.md](09-provider-plugins.md)。
