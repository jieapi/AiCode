# 插件系统计划：构建插件、右抽屉与命令能力

状态：讨论稿。用户已说明构建插件的基本形态，并确认命令目标和授权行为；具体清单字段、页面容器和任务保留策略仍待细化。

## 1. 已确认的产品形态

- 右抽屉展示插件列表，点击条目后打开插件声明的结构化 UI，由 AiCode 绘制。
- 插件配置入口位于“设置 → 插件 → 插件列表”的管理操作中，配置内容使用结构化声明，权限管理使用宿主可信 UI。
- 插件同时提供 UI 声明和业务逻辑，采用声明 + 状态绑定。
- 宿主提供与 AI 一致的 Bash、terminal 通用执行能力，插件用它们实现构建、下载依赖等功能，并能把命令/任务呈现在用户终端页面。
- App 不内置这些具体构建/依赖业务，不硬编码某个语言或框架的命令、下载地址和步骤。
- 插件逻辑和 UI 在手机端；命令跟随当前工作区，本地模式走本地容器，SSH 模式走远端。
- 插件获使用者明确授权后，在授权范围内直接执行命令，不逐条弹窗确认。

建议把“构建插件”视为普通插件提供的页面、配置与命令能力组合，而不是额外的一种原生代码装载机制。插件是否还需要正式分类字段待确认；宿主不能根据名字含“构建”就自动授予命令权限。

## 2. 宿主与插件的职责

| 事项 | AiCode 宿主 | 插件 |
| --- | --- | --- |
| 入口与导航 | 右抽屉列表、来源标识、页面容器、返回和停止等可信操作 | 声明入口标题、展示内容及可选可见条件 |
| UI | 校验声明并使用通用引擎绘制、维护交互状态与事件通道 | 声明布局、样式、字段、按钮、绑定和 handler |
| 配置与管理 | 设置内插件列表、配置/权限等宿主管理操作，以及通用配置存储/提交接口 | 定义自身配置内容、默认值、业务校验和保存时机 |
| 命令执行 | 授权检查、执行目标、通用命令/终端后端、结果与取消 | 决定命令、参数、依赖源、任务步骤和业务成功条件 |
| 状态反馈 | 通用进度、日志和错误组件，受控事件传递 | 把执行结果转换为业务状态和用户可见反馈 |
| 安全 | 管理权限、身份、归属、资源上限和系统/环境限制 | 只能申请和使用获授权能力，不能自己改变授权 |

因此新增构建类型或依赖来源应通过插件发布完成，而不是每次修改 App 的构建命令枚举或下载器业务分支。通用 UI、基础执行能力和宿主权限管理仍由 App 提供。

## 3. 插件声明应表达的内容

不在本轮冻结 JSON/YAML schema，建议先确定这些语义：

- 页面入口：稳定局部 ID、标题、图标/说明、所属插件和页面声明引用。
- 页面声明：布局、表单、绑定、动态列表、按钮事件与业务状态的关系。
- 配置声明：配置字段、值来源、校验与提交 handler；与页面共享 UI 协议。
- 逻辑入口：已打包的业务模块、事件 handler 和可订阅回调。
- 能力申请：Bash/terminal 等所需权限与用途；本地/远端及项目范围不能隐藏在按钮文案里。
- 兼容信息：插件 API 与结构化 UI 协议要求，见分发章节。

“构建”“下载依赖”是插件作者提供的动作和实现，不是必须由宿主认识的标准命令类型。依赖检测、构建步骤编排、错误解释、重试或产物说明均由插件业务决定，不预设宿主实现完整的构建任务图引擎。

## 4. 右抽屉和页面生命周期

当前 [MainActivity.kt:360](../../app/src/main/java/com/aicode/MainActivity.kt:360) 持有一套抽屉状态，[ChatDrawer.kt:146](../../app/src/main/java/com/aicode/feature/agent/presentation/component/ChatDrawer.kt:146) 是会话/文件侧栏；大屏还存在 [MainActivity.kt:716](../../app/src/main/java/com/aicode/MainActivity.kt:716) 的工作台区域。已核实的根布局没有现成的插件右抽屉，不能在计划中写成只向已有插件列表追加一行。

建议新增右侧插件入口，与现有会话/文件侧栏、终端页和大屏工作台协调：

- 清楚展示插件来源、启停和可用状态，列表渲染不启动构建或安装依赖。
- 选择条目后加载声明、建立页面实例和状态，再开放对应事件；不在首次 Compose 重组时自动执行业务动作。
- 列表抽屉与打开后的结构化内容是不同层次；内容在独立页面、抽屉内详情还是大屏工作台展示，仍待用户确认。
- 两侧抽屉的互斥、返回键优先级、边缘手势、键盘和大屏呈现需要统一定义，不能复制一套无协调的抽屉状态。
- 关闭页面只销毁页面订阅还是同时停止任务待确认；不能把页面生命周期直接等同于长命令生命周期。
- 停用/卸载或更新后，旧页面回调不能再操作新插件实例。

## 5. 一次业务动作的建议链路

以某插件提供“构建”按钮为例，仅用于说明宿主/插件分工，不定义 App 内置构建流程：

```text
使用者打开右抽屉 → 选择插件
  → App 校验并渲染页面声明
  → 使用者填写插件表单并点击插件动作
  → 宿主派发事件及页面状态快照
  → 手机端插件 handler 校验业务输入、选择步骤并申请命令能力
  → 宿主检查已授予的插件权限、目标与调用上下文
  → 在当前工作区对应后端执行
  → 输出/退出/失败事件回传插件
  → 插件更新状态，页面按绑定显示进度与结果
```

下载依赖也走同样的通用能力链路。宿主不需要知道该插件在安装哪种 SDK、使用哪个包管理器或构建哪个框架。

点击按钮不是新授权，也不允许执行未声明能力。插件未获得权限时由宿主的权限界面处理；获得授权且范围匹配后，不为每条普通命令再弹一次确认。

## 6. 复用 Bash / terminal 的边界

### 6.1 一次性命令

现有 `Bash` 工具依赖 `CommandEngine`，见 [ExecuteCommandTool.kt:36](../../app/src/main/java/com/aicode/feature/agent/domain/tool/container/ExecuteCommandTool.kt:36)。建议复用后端和可共享的安全校验，新增有插件身份的能力入口，而不是直接调用工具对象的 `execute()` 来绕过其工作流。

打开页面不能自动初始化容器、切换执行环境或安装依赖。后端未就绪、连接不可用或缺少前置环境时，宿主返回明确状态；插件可提供显式业务动作处理其获授权的部分，不把初始化或安装隐含在渲染中。

插件需要结构化结果：输出、真实退出码、超时、取消、异常和截断信息。现有 [CommandEngine.kt:19](../../app/src/main/java/com/aicode/feature/agent/domain/container/CommandEngine.kt:19) 已有结果类型，[CommandEngine.kt:68](../../app/src/main/java/com/aicode/feature/agent/domain/container/CommandEngine.kt:68) 提供带退出码的方法，可作为复用基础；不能仅凭非空输出或 `ToolResult.Success` 判定业务成功。

### 6.2 持续/交互终端

现有 [TerminalSessionProvider.kt:13](../../app/src/main/java/com/aicode/feature/terminal/domain/TerminalSessionProvider.kt:13) 提供启动、输入、输出、控制字符和关闭接口。建议插件获得有归属的任务/终端句柄，不直接得到全局 `tabId` 的无限访问权。

- 只能读取/发送/停止自己持有的任务；列出全部用户终端、接管其他插件终端需要额外明确的能力，不能默认开放。
- 持续输出、完成和失败通过有界回调交给插件，不能把反复扫描终端屏幕当作唯一的实时日志协议。
- PTY 输出包含控制序列、可能被屏幕缓冲截断，和完整命令日志不是同一种数据，需要明确向插件返回什么。
- `send`/控制键也可能改变进程行为，属于权限和归属检查范围，不只是 `start` 检查。
- 退出状态不明、连接断开和取消不能统一当成功；停止请求需要确认真实执行结果。

已有后台完成事件的来源是 AI 会话，见 [TerminalTab.kt:24](../../app/src/main/java/com/aicode/feature/terminal/domain/TerminalTab.kt:24)。插件任务需增加自己的来源和事件路由，不能为了接收完成事件伪造会话 ID，或自动向 AI 注入消息、启动推理。

### 6.3 与用户终端页面共享

**已确认：与 AI 使用相同的 Bash/terminal 能力，新建共享标签即可，使用者在终端页面查看和交互。** 不需要插件接管使用者已有标签，也不创建仅在插件内部可见的私有终端。

现有 AI terminal 通过共享 provider 创建标签，用户终端页也读取相同管理器的标签，见 [DelegatingTerminalSessionProvider.kt:24](../../app/src/main/java/com/aicode/feature/terminal/domain/DelegatingTerminalSessionProvider.kt:24)、[TerminalViewModel.kt:68](../../app/src/main/java/com/aicode/feature/terminal/presentation/TerminalViewModel.kt:68) 和 [TerminalScreen.kt:100](../../app/src/main/java/com/aicode/feature/terminal/presentation/component/TerminalScreen.kt:100)。插件应复用这条链路，在标签和完成事件中增加归属，而不是另起终端后端。

建议明确以下三种操作，避免“发送到终端”导致重复执行：

- 启动 terminal 任务：创建共享标签，使用者可在终端页面查看、输入或停止；插件仅持有授权句柄。
- 查看已有插件 terminal 任务：打开终端页面/大屏终端区域并聚焦原标签，不重新运行命令。
- 将一次性 Bash 命令改为在终端执行：保持 Bash 和 terminal 原有语义；已经完成的 Bash 不能伪装成可迁移的存活会话。若明确要求在终端重新执行，这是新执行动作，仍需检查插件授权与目标。

发送命令采用新建共享标签的范围，不增加选择/注入使用者已有交互标签的功能；查看插件自己已经创建的标签仍然是聚焦原任务。是否默认抢焦点或自动打开页面尚未确认。

现有标签激活可参考 [TerminalSessionManager.kt:278](../../app/src/main/java/com/aicode/feature/terminal/domain/TerminalSessionManager.kt:278)，页面打开走 [MainActivity.kt:547](../../app/src/main/java/com/aicode/MainActivity.kt:547) 的工作台/全屏入口。后者在大屏上是 toggle，插件定位已有任务应采用“确保打开并聚焦”的语义，不能无条件复用 toggle 把正在看的终端收起。当前路由与 TerminalScreen 没有指定 tab 参数，需要在实施时补接，不写成已有完整能力。

共享给使用者查看不等于共享给所有插件：宿主 UI 可以管理标签，插件 SDK 的读写/关闭仍按归属和授权校验。使用者关闭标签后，插件得到真实的关闭/停止状态，不能继续将其视为运行中。

## 7. 执行目标与切换一致性

**已确认：命令跟随当前工作区；插件逻辑仍在手机。**

现有 [DelegatingCommandEngine.kt:24](../../app/src/main/java/com/aicode/feature/agent/domain/container/DelegatingCommandEngine.kt:24) 和 [DelegatingTerminalSessionProvider.kt:32](../../app/src/main/java/com/aicode/feature/terminal/domain/DelegatingTerminalSessionProvider.kt:32) 会在调用时按当前模式选择后端。

建议在启动动作/任务时绑定宿主生成的执行上下文：本地容器或 SSH 连接身份、工作区、工作目录和授权范围。已启动句柄后续读取、输入、取消都指向原目标，不因当前页面切到另一工作区就操作另一后端。

切换后新发起动作使用新工作区并重新检查授权匹配；旧任务能否继续运行与能否继续启动后续步骤需要明确，不静默把同一任务迁到新目标，也不把授权范围默认扩大到所有服务器。

## 8. 命令授权与 AI 审批分离

**已确认：插件在获授权范围内直接执行，不逐命令确认。** 这是插件 UI 业务调用的规则，不改变已确认的 AI 工具代审核规则。

- 插件 UI 动作：声明能力 → 用户授权 → 每次调用检查范围 → 匹配则直接执行。
- AI 调用工具：仍先由宿主判断，只有 ASK 才进入顺序代审核链。
- AI 调用插件工具时，外层 AI 审批和内层插件能力检查都保留；后者不会额外弹出每条普通命令确认。
- 来自受限 Agent 的调用上下文必须保持来源和模式限制，不能冒充真实用户 UI 事件来绕过 PLAN。
- 是否给显式用户 UI 动作附加当前 AI 模式限制需要单独确定，不能默认把 UI 点击当作 AI 请求，也不能据此放开受限 Agent。
- 越权、撤权、目标变化或宿主需要特殊处置的操作不属于普通授权范围；拒绝或额外申请必须明确，不能自动提权。

Bash 和 terminal 命令权限不等于 Shizuku 授权，命令目标也不包括直接操作宿主 Android。Shizuku 的单独规则继续见权限章节。

## 9. 沙箱与依赖下载的安全说明

隔离的是手机端插件逻辑，不是已经授权启动的任意命令。命令可按所用后端和系统权限读写文件、联网或启动子进程；SDK 的文件/网络接口授权不能限制命令内部的一切行为。

因此命令权限应明确描述实际信任范围，不能仅用一个工作目录、命令前缀或“只用于构建”的文字就承诺强隔离。项目依赖安装也可能执行上游安装脚本，风险由插件功能和命令授权明确呈现。

插件主逻辑依赖建议发布前打包；插件外部服务的 npm/pip 依赖已确认可由用户手动准备到独立目录/虚拟环境，不在本轮自动安装系统工具。构建插件为用户项目下载 SDK/依赖仍是另一个已确认业务场景，发生在其授权能力范围内；这些都不能与“解压插件包时执行任意 install 脚本”混为一谈，见 [12-service-dependencies.md](12-service-dependencies.md)。

## 10. 在途任务与恢复待确认

建议明确以下行为后再冻结任务接口：

- 返回聊天、关闭页面或收起右抽屉后，任务继续还是停止。
- 插件停用、撤权、更新、卸载时的停止与等待边界。
- 同一动作是否允许重复/并行启动，取消后能否重试；避免重组引起重复执行不代表禁止业务主动重试。
- App 被系统杀死、SSH 断线或容器变化后如何报告状态；不在没有验证时承诺任务自动续跑。
- 任务日志和产物引用的保留、清理和读取权限，不能无限增长或误删工作区产物。

这些是通用执行设施应说明的生命周期，不要求宿主内置插件业务步骤或构建配方。
