# 插件系统计划：提供商注册与兼容接口

状态：讨论稿。已确认支持提供商插件；插件对接 App 当前支持的接口，上游协议由插件处理。兼容 HTTP 服务、进程管理和具体清单字段为接入建议，尚未实现或定稿。

## 1. 已确认的边界

- 插件可以注册提供商，这与工具、MCP、Skill、子代理、页面等一样，是普通插件的一类贡献。
- AiCode 只消费自己当前支持的提供商接口，不因为插件上游特殊就新增 `ProviderType` 或内置新的上游适配器。
- 插件上游可以使用其他协议；请求转换、鉴权、响应/流式事件转换等由插件实现，不把上游限制为 App 的三类格式。
- 插件可以使用已提供的执行环境与获授权能力完成这些业务；不等于可以读取所有渠道凭据或绕过插件权限。

```text
AiCode 现有提供商接口
  ↔ 插件提供的兼容接口
  ↔ 插件自己的上游请求、鉴权与协议转换
  ↔ 实际上游服务
```

这里的“兼容接口”是插件面向 AiCode 的一侧；它与插件实际连接的上游协议不能混为一个字段或概念。

## 2. 建议的接入方式

建议插件注册名称、稳定局部 ID、App 侧兼容格式、服务入口与模型信息；App 继续走现有供应商配置、模型选择和调用链。

- 对外部已兼容服务，可直接声明对应入口，不强制所有提供商都另起本地转换进程。
- 需要转换时，建议插件通过获授权的运行环境启动一个兼容 HTTP 服务，或提供其受管理的服务入口，再由 App 现有适配器访问。
- 上游适配逻辑留在插件或插件管理的服务中，不把任意插件代码当成 App 主进程内的新 `AIProvider` 实现。
- 具体采用哪种服务托管、如何启动、发现就绪和解析动态地址仍需明确；不在本轮假定兼容服务已经天然存在。
- 宿主启动已选提供商的兼容服务与 AI 请求执行 shell 工具不是同一调用来源，启动/请求上下文应由宿主绑定；不能让插件伪造服务来源消除 AI 工具的模式限制。服务在 PLAN 会话中的初始化规则要在 SDK/执行策略中单独验证。

插件运行时与其启动的服务进程是不同层次。“完整环境”表示可使用现有容器、命令与已授权运行能力，不保证每台设备已安装全部解释器或依赖；也不能把这些进程宣称为 JavaScript 沙箱的一部分。已确认外部服务依赖由用户点击准备，environmentRef 关联的环境 ready 后才启动，缺解释器不自动安装系统工具，见 [12-service-dependencies.md](12-service-dependencies.md)。

此前已确认插件逻辑在手机、命令跟随当前工作区。本地模式下使用容器服务可作为方案；SSH 模式中，App 如何访问插件启动的远端服务，需要定义明确可达入口或受控转发，不能直接把远端 `localhost` 当成手机 `localhost`。这项部署细节待定，不更改已有执行环境决策。

## 3. 插件清单与结构规范需要覆盖的语义

[10-plugin-format.md](10-plugin-format.md) 已在统一清单中加入 providers/services 及完整引用示例，[11-index-format.md](11-index-format.md) 包含对应贡献预览。以下是提供商字段语义，具体 SDK 与服务托管仍待细化，不表示宿主已经实现。

| 内容 | 作用 |
| --- | --- |
| 提供商局部 ID 与展示名称 | 与插件身份组合形成稳定归属，不按名称覆盖其他渠道 |
| App 侧兼容格式 | 选择当前支持的格式及相应请求模式，不声明 App 不认识的新类型 |
| 入口或入口解析方式 | 外部固定地址，或受管理兼容服务就绪后解析的地址 |
| 模型与能力信息 | 支持已有模型添加/选择流程，能力不能只按名称猜测 |
| 配置声明引用 | 使用已有结构化配置机制收集该插件所需业务配置 |
| 凭据需求与授权 | 明确哪些配置/凭据会交给插件或兼容服务，不能默认获取其他渠道信息 |
| 服务生命周期引用 | 启动、就绪、异常、取消和停止与提供商可用状态的关联 |
| 插件/协议兼容版本 | 更新时验证兼容接口与服务部署是否仍可用 |

实际的上游地址和协议属于插件业务配置，不要求 App 理解它们或在索引中执行它们。索引只记录插件元数据和贡献摘要，不存放提供商转换业务代码。App 侧兼容格式与选项需要严格校验，未知值应拒绝，不能静默按某个现有类型兜底。

## 4. 注册、使用与生命周期（建议）

1. 安装/启用插件，核对其注册提供商及所需执行、网络或凭据能力。
2. 宿主注册有插件归属的提供商定义/条目，不覆盖内置预设或使用者手工渠道。
3. 使用者在现有提供商流程中配置并选用对应实例；是否自动创建实例、初始模型和默认选择仍需明确，不默认切走当前供应商。
4. 调用前确保兼容服务就绪、入口与版本匹配，再走 App 原有模型请求。
5. 服务失联、插件停用/撤权/更新或卸载时，及时更新该条目的可用性并处理在途请求。

共享服务的多个提供商实例和并发请求需要独立关联；停止某个实例不能误停其他实例或插件服务。版本切换不能把旧请求转发到不匹配的新服务。

卸载时清理插件拥有的定义与连接，不直接删除使用者创建的独立渠道、模型配置或其他插件的服务。用户配置保留、迁移和在途请求停止方式尚需定稿。

## 5. 凭据与数据边界

- 提供商会处理模型请求和响应，需在使用/授权时明确其可见的数据；注册不是普通无副作用的展示操作。
- 上游凭据可能必须由插件处理，不能承诺插件看不到自己业务所需的凭据；应仅交付使用者明确配置/授权给该插件的凭据。
- App 到兼容服务的认证，与兼容服务到实际上游的认证可以分开；不能默认把所有渠道 Key 原文或活动渠道对象交给插件。
- 如使用本机兼容服务，建议限制监听范围并使用适当认证；仅有一个可猜端口不能构成访问控制。
- 动态入口、鉴权配置或上游目标变化应重新核对权限范围；日志不得复制凭据或完整聊天内容。
- 该贡献不能自动获得模型调用、网络、命令执行或用户配置修改的全部权限；实际所需权限由执行路径明确声明。

## 6. 现有代码依据与需要适配的边界

- [AIProviderConfig.kt:138](../../app/src/main/java/com/aicode/feature/settings/domain/model/AIProviderConfig.kt:138) 定义现有 `ProviderType`；[StatefulAgentWorkflow.kt:280](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:280) 按类型创建 App 内置适配器，并应用地址、模型、Key 和请求选项。兼容接口方案复用这条链路，不添加未知上游类型。
- [ProviderPresetLibrary.kt:12](../../app/src/main/java/com/aicode/feature/settings/data/local/ProviderPresetLibrary.kt:12) 是现有名称/格式/地址/模型等预设信息；[AIProviderRepository.kt:6](../../app/src/main/java/com/aicode/feature/settings/domain/repository/AIProviderRepository.kt:6) 管理真实配置。插件贡献须保留自己的来源/归属，不能仅将预设追加到列表就视为服务已经可用。
- [StatefulAgentWorkflow.kt:222](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:222) 当前要求可用 Key 和模型。兼容服务如何认证需正确适配，不能用假 Key 掩盖认证模型缺失。
- [StatefulAgentWorkflow.kt:234](../../app/src/main/java/com/aicode/feature/agent/domain/workflow/StatefulAgentWorkflow.kt:234) 当前在绑定提供商配置不存在、禁用或模型绑定失效等情况下可能回退默认配置，不是任意网络失败都会触发回退。插件停用/失效若影响这些绑定，必须明确提示并确定回退策略，不能无感把请求和费用转到其他上游。

现有内置提供商预设仍按项目约定维护；插件来源单独管理，不改写 `data/providers.json` 或内置快照来伪装成内置官方提供商。本轮不修改任何生产数据、应用代码或配置。

## 7. 建议验收

- 插件提供 App 已支持的兼容接口，但实际连接其他上游，App 无需增加新的上游适配器即可调用。
- 注册、配置、模型选择、测试与实际调用所用的服务入口和插件版本一致。
- 服务未就绪、退出或失去授权时不误报可用，不静默回退到其他付费渠道。
- 流式输出、工具调用/结果、错误、取消和 usage 等兼容行为按 App 当前能力完成契约测试，不能只验证一次普通文本成功响应。
- 仅处理该插件获授权的请求、配置和凭据；停用/卸载不破坏用户手工渠道或其他插件实例。
- 本地/SSH 场景的服务地址真实可达，进程与请求取消有明确结果，不把网络超时当作服务已停止。
