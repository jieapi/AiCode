# 插件系统计划：服务依赖与手动准备环境

状态：讨论稿。已确认支持插件外部服务依赖，由使用者点击“准备环境”触发；不把系统工具自动安装加入本轮范围。环境字段和状态细节为结构草案，不是已实现能力。

## 1. 依赖分层与已确认范围

| 依赖类型 | 本轮规则 |
| --- | --- |
| 插件主入口的 JavaScript 依赖 | 建议由作者发布前 bundle；容器中安装 npm 包不使隔离运行时自动获得 Node 模块 |
| 插件外部服务的 npm/pip 等依赖 | **已确认支持**；独立目录/虚拟环境，用户手动准备，所需解释器与包管理器由现有环境提供 |
| 用户项目的构建依赖、SDK 等 | 保持已确认的插件业务能力，通过授权后的 Bash/terminal 执行；与插件自身服务环境分开 |
| 为插件服务自动安装 Node/Python/JDK 等系统工具 | **不纳入本轮服务依赖准备机制**；缺少前置工具就报告缺失，不偷偷安装或改系统 |
| 插件之间的依赖 | 尚未提出，不在本轮加入依赖求解器 |

“插件能安装依赖”指获授权的服务依赖准备或项目业务操作，不是在解压 ZIP 时执行任意 install 脚本，也不是下载代码后直接注入 App 主进程。

## 2. 使用者流程（已确认手动触发）

```text
安装插件并完成来源确认与能力授权
  → 显示插件和服务依赖状态
  → 使用者点击“准备环境”
  → 宿主确认本次插件版本、依赖输入与执行目标
  → 检查解释器/包管理器等前置条件
  → 创建该目标下的受管理服务环境并执行准备 handler
  → 校验准备结果与检查结果
  → 标为 ready，允许依赖它的服务启动
```

- 不在安装预览、解压、模块加载、页面渲染或普通模型请求时自动安装依赖。
- 用户未准备时可以管理插件、查看状态；仅依赖该环境的服务和贡献不可用，不误报整个插件损坏。
- 已授权范围内执行准备步骤不逐命令弹窗；准备按钮不是申请所有新权限的总授权。
- 解释器或包管理器缺失时显示具体缺项，准备保持未就绪；不改源、不降版本、不删锁文件强装。
- 日志、进度、失败与重试入口可见，使用者可以取消；取消等待不等于底层进程已经停止。

## 3. 新的环境声明

在 `contributes.environments` 放服务依赖环境，与服务本身分开；服务通过 `environmentRef` 引用，实例绑定当前工作区后端。统一完整样例已同步到 [10-plugin-format.md](10-plugin-format.md) 与 [11-index-format.md](11-index-format.md)。

| 字段 | 语义 |
| --- | --- |
| `id` | 插件内稳定环境 ID |
| `target` | 本草案为 `currentWorkspace`，由宿主绑定本地容器/SSH 与工作区 |
| `manager` | 草案为 npm/pip，确定锁文件与严格安装语义 |
| `prerequisites` | 已需存在的可执行程序名，只检查，不授权系统安装 |
| `inputs` | 发布包内的只读资源条目，含包根相对 path 与原始字节 SHA-256 |
| `lockFiles` | inputs 中参与版本锁定的文件，相对包根，必须包含在包和摘要中 |
| `checkHandler` | 检查环境与依赖是否满足需求，不负责自动修复 |
| `prepareHandler` | 只有用户明确准备/重试时才执行的安装逻辑 |

check/prepare 的 JavaScript handler 仍运行在手机；检查和安装命令才跟随已绑定的工作区后端，不能把插件运行时迁到远端。

服务的 `environment` 与所引用环境的 `target` 必须一致；不能给本地已准备状态，却在 SSH 后端直接标为就绪。`environmentRef` 也不能引用其他插件的私有目录。

包中的资源和锁文件保持只读。准备时仅将声明的 inputs 提供到该目标下的受管理环境工作区，依赖与缓存写入宿主分配的目录；不写回发布包，不把配置/上游密钥放进锁文件。

这个受限的服务资源发布用途由 `environment.prepare` 管理，不意味着开放任意文件同步，也不改变 Skill 附带资源的未决策略。

### 严格安装语义（草案）

- npm：inputs 包含 package.json 与 package-lock.json，lockFiles 引用后者；按 npm ci 的锁定语义准备，不用 npm install 改写锁文件。锁格式或 integrity 不支持时报告，不自动升级包管理器或生成新锁。
- pip：inputs/lockFiles 引用完全固定版本并提供包哈希的 requirements 锁文件，按 --require-hashes 的语义安装到独立 venv；不支持的来源/完整性或缺少构建工具时报告，不偷装系统依赖。
- 路径均相对于发布包根，准备工作目录由宿主分配；锁文件不因为安装失败而被重写。包管理器/锁格式具体支持矩阵仍需验证，不在本轮执行上述命令。

## 4. 权限与执行边界

新增草案权限 `environment.prepare`，scope 为 `{ids: [环境ID]}`，用途与执行目标向使用者展示。它只允许准备已声明的环境，不是通用系统管理授权。

如果 prepareHandler 经 Bash/terminal 执行命令，还需要实际命令/终端能力；handler 不因处于准备流程就自动获得网络、全局存储、Shizuku 或其他渠道凭据。

- 网络下载与安装脚本的风险需要展示，锁文件和版本固定不能证明依赖无恶意。
- npm/pip 等安装可能执行依赖提供的脚本，是否允许、如何呈现是执行策略需明确的风险，不能把它们视为纯文件下载。
- 独立目录或虚拟环境是依赖和版本管理方式，不是安全沙箱。任意已授权 shell 进程可能访问其后端本来可访问的其他资源，SDK 权限无法约束命令内部所有行为。
- 不能只检查命令前缀或设置 cwd 就承诺“只能写这个目录”；实际权限范围必须诚实说明。
- 撤销准备权限阻止新的准备/重试；服务执行授权与已准备资源的使用另行检查，在途进程停止/等待策略仍需定稿。

## 5. 环境实例与就绪判定（建议）

宿主的准备记录至少绑定：安装身份、插件版本/包摘要、环境 ID、inputs/锁文件摘要、执行后端/容器或服务器身份、工作区、前置工具版本与本次准备结果。

```text
notPrepared
  → checking
      ├─ missingPrerequisite
      ├─ ready（已有环境核验通过）
      └─ preparing
          ├─ ready
          ├─ failed
          └─ cancelled
```

检查发现已有环境满足条件时可进入 ready，不必重复安装；具体复用策略必须验证相同目标、版本与输入。checkHandler 的业务判断不是宿主安全认证，宿主仍检查关联身份、过程结果和有效授权。

- 依赖未准备时，provider/MCP/服务需要明确的不可用原因，而不是先启动后循环失败。
- 版本、锁文件、前置运行时或执行目标变化后重新检查，不直接沿用旧 ready。
- 准备失败不能切换到另一份“碰巧可用”的系统全局依赖，也不能把部分安装当成功。
- 同一环境实例并发准备要串行/去重；不同插件或目标不能共享未声明的可写目录。
- App 重启后先核验实际状态再使用缓存标记，不声称 prepared 状态等于进程仍在运行。

依赖准备完成与服务启动分开；服务可以按调用需求启动，但不能把未准备的环境自动补装后继续。

## 6. 索引预览与锁文件

索引中不放 lock 文件内容或安装脚本；版本包携带它们。版本记录预览列出环境 ID、目标、前置程序、输入/锁文件路径、检查/准备入口以及权限依赖，必须与真实清单一致。

ZIP/manifest 摘要和包内锁文件原始字节用于确定准备输入。下载后发现输入或准备声明与预览不一致时拒绝旧确认，不允许“已确认插件地址”覆盖所有后续依赖变化。

具体包版本由锁文件和作者测试保证；示例不假定某个实时版本或镜像可用。安装依赖失败时报告原因，不能自行修改锁文件重试。

## 7. 更新、清理和失败恢复待细化

已确认必须由用户手动准备，但以下策略尚未决定：

- 更新后何时复用或重新准备环境，旧服务/环境等待到何时清理。
- 卸载、停用和撤权对运行服务及缓存的保留/停止规则。
- 下载缓存、日志和环境空间上限，重试/超时与磁盘不足处理。
- 外部依赖来源与完整性策略、安装脚本执行策略及离线准备能力。

这些不应反过来把系统工具自动安装变成默认能力；也不允许在撤权后执行任意插件清理脚本。宿主只删除自己有归属的资源，不清理用户项目或系统环境。
