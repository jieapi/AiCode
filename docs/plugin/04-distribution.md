# 插件系统计划：多索引仓库、官方标识与在线安装更新

状态：讨论稿。多索引、一插件一独立仓库、在线安装更新和非官方逐次手输确认已确认；“官方”的认定规则仍是建议，用户尚未决定。本轮不创建仓库或发布产物。

## 1. 已确认的分发结构

```text
App 配置的多个插件索引仓库
  → 每个索引只记录插件条目和版本元数据
  → 条目指向该插件独立的源码仓库与版本包
  → App 展示来源、官方状态、版本和权限
  → 使用者确认后在线安装 / 更新
```

- 使用者可以配置多个插件仓库；这里称为“索引仓库”，避免与插件源码仓库混淆。
- 索引仓库只存放索引，不集中存放所有插件源码或运行产物。
- 每个插件有自己的独立源码仓库，版本包由该插件的发布流程提供。
- 索引条目要能展示是否为官方插件，但最终官方认定不能在未决状态下偷偷定案。
- 非官方插件每次安装、每次在线更新都显示确认弹窗，并要求使用者输入该插件的源码仓库地址。
- 本轮确认在线安装和在线更新，不代表已授权无交互自动安装更新。

AiCode 主仓库维护宿主、SDK/协议和兼容测试；官方索引建议使用独立仓库管理。具体仓库名称、实际地址与发布 ref 未定，不在本轮创建或臆造；目录与索引入口已给出具体草案，见 [11-index-format.md](11-index-format.md)。

## 2. 三类地址必须区分

| 地址 | 用途 | 是否是非官方手输确认对象 |
| --- | --- | --- |
| 索引仓库地址 | 找到可安装条目及版本，标识目录来源 | 否 |
| 插件源码仓库地址 | 确认插件作者与插件自身的独立来源 | **是，已确认** |
| 版本包下载地址 | 下载选定版本的实际安装包，可由发布存储/CDN 承载 | 否，仍须核验内容与来源对应关系 |

不能拿索引地址、压缩包地址或插件名称替代源码仓库地址，也不能用展示名相同就继承另一仓库的授权。

## 3. 多索引配置与聚合（行为建议）

设置内插件管理提供仓库配置入口，详见 [08-plugin-management.md](08-plugin-management.md)。每个索引来源至少需要稳定身份、显示名称、地址、启用状态、刷新状态与上次成功结果；是否支持认证和其他传输形式尚未决定。

- 按来源分别拉取、校验、缓存和报告错误，一个来源不可用不拖垮其他来源或已安装插件。
- 列表保留来源，安装记录绑定选中的源码仓库、索引来源、版本和包摘要；不把同名条目静默合并。
- 多个索引声称同一插件时，只能在发布身份、源码仓库和版本内容一致后合并展示；不一致的条目需要显示冲突，不能全局取最高版本覆盖。
- 已安装插件的更新沿已绑定来源检查，不因新增一个同名索引条目而换源或继承新作者身份。
- 禁用/删除索引后如何处理已安装插件的更新入口需明确；建议停止使用该来源发现更新，而不是自动卸载正在使用的插件。
- 多来源排序或优先级尚未决定；来源顺序不能替代插件发布身份和官方认定。

现有 [RepoDataFetcher.kt:21](../../app/src/main/java/com/aicode/core/net/RepoDataFetcher.kt:21) 支持 owner/repo/branch，但磁盘缓存键目前只按路径生成，见 [RepoDataFetcher.kt:173](../../app/src/main/java/com/aicode/core/net/RepoDataFetcher.kt:173)。多索引不能直接共用这个缓存身份，需区分来源并先校验内容，避免不同仓库的同名文件互相污染。

现有镜像任务的 `data` 分支是生成型最新快照，见 [sync-container-images.yml:67](../../.github/workflows/sync-container-images.yml:67)。插件索引还需要审查历史、版本追溯和撤回记录，不建议将这种最新快照分支作为唯一事实源。

## 4. “官方插件”认定：建议与待定项

**当前状态：用户尚未决定认定标准。** 以下为推荐方案，不是已确认决策。

### 4.1 建议将两种标识分开

- **AiCode 官方插件**：由 AiCode 官方维护、以可信官方发布身份确认的插件。
- **来自官方索引 / 官方收录**：只是该条目由可信官方索引提供，不等于插件由官方开发维护。

这样官方索引可以收录社区插件，但社区插件仍属于非官方，安装和每次更新都执行手输确认。不能为了减轻安装步骤，把“官方收录”直接显示成“官方插件”。

### 4.2 建议的技术判定边界

- 索引中可以包含声明性的官方字段或发布者信息，但客户端展示的官方身份需要由宿主认可的可信来源/发布记录核验，不能只相信任意索引的 `official=true`。
- 普通自定义索引不能靠名称、作者文本、图标、相同 ID 或源码 URL 给任意包授予全局官方身份。
- 身份核验还需匹配源码仓库、版本和安装包内容，防止一个索引引用官方仓库名称却下载修改过的产物。
- 正式分发建议采用可验证的官方发布元数据或签名记录。信任根、密钥轮换、离线验证和具体签名格式待选型，不在本轮定算法或填入公钥。
- 自定义索引镜像一个真实官方版本时是否沿用官方标识，取决于能否核验同一可信发布记录；尚未核实时不据此跳过非官方确认。

该方案主要避免第三方索引伪造官方身份，同时不把“官方”承诺成没有风险。官方插件仍需声明权限并由使用者授权，也仍受运行时和宿主能力限制。

如果用户最终选择“官方索引收录即官方”，需要同步改写标识含义和确认条件；目前不擅自采用这种定义。

## 5. 索引与版本元数据

具体 JSON 文件、字段与完整示例已在 [11-index-format.md](11-index-format.md) 给出草案；下表是分发语义总览，格式仍待审阅，不表示只停留在字段方向。

| 类别 | 必要语义 |
| --- | --- |
| 来源 | 索引来源身份、插件独立源码仓库、发布者身份、源码版本对应关系 |
| 身份与展示 | 插件 ID、名称、作者、简介、许可证、官方声明与核验状态 |
| 版本 | 插件版本、插件 API / UI 协议兼容范围、最低 App/运行时要求 |
| 内容 | 包摘要、大小、下载位置；页面、配置、handler、提供商等贡献及服务启动声明的完整性 |
| 权限 | 声明的能力、用途、必要/可选、范围及相对已安装版本的变化 |
| 状态 | 维护状态、风险提示、撤回与可用替代版本 |

索引仓库只保存这些索引内容；插件源码、UI/配置声明、提供商贡献和已打包业务逻辑由插件独立仓库及其版本包持有。提供商上游转换代码不放进索引运行，也不改写 App 的内置提供商预设。

同一插件版本对应唯一内容摘要，不允许替换同版本包后复用旧确认与授权。是否要求全部插件开源、本地包导入、认证索引等仍待确认；多自定义索引支持本身已确认，不再列为未定需求。

## 6. 非官方插件的逐次确认（已确认）

### 6.1 交互规则

1. 使用者点击某个非官方插件的安装或更新按钮。
2. 宿主弹出确认界面，显示插件名称、所选版本、源码仓库地址、索引来源、风险和权限摘要。
3. 使用者手动输入该插件源码仓库地址。
4. 输入与本次目标来源匹配后，才允许最终确认；输入为空、不匹配或取消时不继续安装/更新。
5. 每次非官方更新都重新执行，不能复用首次安装的确认，也不能由代审核插件自动确认。

输入框不自动填好目标地址。是否允许粘贴、支持哪些仓库 URL 写法和规范化规则尚未确认，不能把“手动输入”擅自收窄为禁止粘贴，也不能放宽为一个勾选框。

### 6.2 建议的校验与绑定

- 按完整仓库身份比较，至少区分主机与仓库命名空间；不能只比最后一段名称、子串或显示文本。
- 仅规范化已确定等价的地址形式，不随意去掉路径、大小写、查询等信息后误把不同来源判为相同。具体 HTTPS/SSH 等形式支持范围待定。
- 确认绑定本次插件、源码仓库、索引来源、版本、包摘要、权限声明及官方核验结果；目标或相关信任状态变化时废弃旧确认并重新展示。
- 弹窗由宿主渲染和校验，不能用插件自定义 UI 替换，也不能接收插件发来的“已输入正确”标志。
- 后续下载/校验要核对同一个目标，不能输入一个仓库地址后由索引重定向到另一插件而继续复用确认。

手输地址是使用者确认安装意图的机制，不是安全签名、源码审计或沙箱，不能替代后面的完整性、身份和能力授权检查。

## 7. 在线安装流程

```text
刷新一个或多个索引 → 选择明确来源和版本 → 点击安装
  → 显示宿主安装信息与权限摘要
  → 非官方：确认弹窗 + 手输插件源码仓库地址
  → 使用者最终确认
  → 下载到临时区，核验包、兼容性与路径安全
  → 核对已展示声明，完成插件能力授权
  → 原子安装并激活获授权的贡献
```

官方插件也不跳过权限授权和包校验；它是否省略普通安装确认尚未决定，只确认了非官方额外的手输门槛。

下载、校验失败或新内容与已确认元数据不一致时不激活，不执行第三方安装脚本，也不保留可被误当成已安装的半成品状态。权限授权前不能启动 MCP stdio、执行命令或业务 handler。

包处理限制压缩/解压大小、单条目大小、条目数和路径深度；流式读取时执行限额，拒绝越界、危险链接和混淆条目。现有 [SkillImport.kt:146](../../app/src/main/java/com/aicode/feature/agent/domain/skill/SkillImport.kt:146) 可提供参考，但不能不经审查直接作为代码包安装器。

插件主逻辑依赖建议发布前打包；外部服务依赖已确认可在用户手动准备阶段安装，索引预览与包内依赖输入须核对。项目下载 SDK/依赖仍是另一个已授权业务场景，不等于插件安装/预览时执行任意 install 脚本，见 [12-service-dependencies.md](12-service-dependencies.md)。

## 8. 在线更新流程

**已确认：支持在线更新；每次非官方更新均需确认弹窗并输入源码仓库地址。** 因此不能对非官方插件提供跳过这一步的无交互自动更新。

- 列表区分已安装版本与可用版本，展示更新来源和兼容/权限变化。
- 更新沿绑定来源获取，非官方每次重新输入，即便仓库没变也不免除。
- 新增或扩大权限另行取得使用者同意；手输来源不代表同意全部新权限。
- 来源、发布身份或包内容身份变化不得静默继承原授权；先重新核验并显示变化。
- 校验与授权完成后一致切换插件实例、贡献、MCP、页面与回调；失败保留原可用版本，避免半更新。
- 已运行任务如何等待/停止，以及运行数据迁移和回滚支持，仍需明确；回滚包不能撤销已发生的外部副作用。
- 若提供批量更新，非官方插件仍逐个完成自己的确认，不能输入一次地址替整批放行。

检查更新可以与真正应用更新分开。是否后台自动检查、官方插件是否支持自动应用等策略仍待确认，不因“在线更新”直接推导。

## 9. 停用、撤权与卸载

- 停用/撤权阻止新的受保护调用，使待执行旧授权失效，移除相应监听和入口。
- 清理属于插件的 MCP 连接、通知、回调和安装内容，不修改使用者手工配置或其他插件贡献。
- 在用户终端中可见的插件任务也必须保留归属；停用/卸载时停止、等待或保留何种任务状态待确定，不按显示标题批量关闭标签。
- 是否删除插件运行数据由使用者可理解的行为决定，不能误删工作区产物。
- 不在撤权或卸载后执行任意第三方清理脚本。

## 10. 发布与风险处置（建议）

1. 作者在插件独立仓库发布源码与版本包；索引提交相应元数据和权限说明。
2. 校验索引格式、身份唯一性、版本对应、包摘要和权限变化。
3. 可信索引维护者按自身规则审查，官方身份还须符合最终确认的认定规则。
4. 发布可追溯索引，不把目录收录视为插件安全证明。
5. 风险版本可标记或撤回，App 自动停用/提醒/继续运行的策略待确认。

PR、索引和插件包都作为不可信输入。校验索引不运行插件脚本；动态测试如有需要，使用隔离任务，不接触发布密钥、生产凭据或仓库写权限。

包摘要只证明与元数据一致，不能单独证明元数据未被篡改；建议正式目录分发确定可验证元数据、信任根、轮换、过期和离线策略。CDN 仅承担传输，不因为使用某个域名就跳过最终核验。

## 11. 合规与开发闭环（待决策）

### 11.1 F-Droid

项目在 F-Droid 上架。其收录政策（Inclusion Policy，第 5 条）要求：应用**不得在没有明确用户同意的情况下下载额外的可执行二进制文件（如 add-ons、自动更新）**；同意必须是 opt-in，拒绝不能比接受更难，且要向使用者讲清他们是在绕过 F-Droid 的检查。另有 `NonFreeAdd`（Non-Free Addons）反特性，针对“推广非自由附加组件或插件”的应用。

- 第一切片只从本地文件导入、不联网下载，不触发这一条；
- 在线索引安装 / 更新上线前必须评估：JS 包是否算“可执行二进制”（**未核实**，需要向 F-Droid 维护者确认，或把在线分发做成 flavor / 默认关闭的开关）；
- “是否要求全部插件开源”会直接影响 Non-Free Addons 的判定，应与该决策一并确定；
- 同意界面必须清楚说明“插件来自第三方、不经过 F-Droid 审核”。

### 11.2 插件 SDK 许可证

主项目是 GPL-3.0。SDK 的类型声明与辅助库会被打进插件包分发，许可证未定会让插件作者不确定自己的插件是否被 GPL 传染。需要在发布 SDK 前明确（候选的宽松许可证与 GPL-3.0 的关系应单独评估）。

### 11.3 本地侧载与开发闭环

第一切片的本地导入已经是一条不经仓库来源的安装路径，而非官方在线安装每次要手输源码仓库地址（R22 / R24），开发迭代时不可行。后续是否需要独立的“开发者模式”（显式开启、醒目标识、不参与更新）需要决策。除此之外作者还缺：SDK 类型包、清单校验与打包的命令行工具、以及让 AI 帮忙生成并校验插件的内置技能——安装和授权始终只能由使用者在宿主界面完成，AI 不能代批。
